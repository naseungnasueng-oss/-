# ROOM1 필드 아이템·인벤토리 UX 수정 플랜

**상태:** 순차 실행 준비 완료. 각 단계는 별도 검토·검증·로컬 커밋으로 진행하며 push하지 않는다.

**이해한 요청:** ROOM1의 기존 퍼즐 정답과 진행 규칙은 유지하되, 획득 가능한 아이템을 배경과 분리된 레이어로 표시하고 `확인/획득` 흐름을 제공한다. 공통 인벤토리는 화면 하단의 작은 패널로 바꾸고, 아이템 정보 확인과 휴대폰의 명시적 사용을 지원하며, 인벤토리 밖 클릭으로 안전하게 닫히게 한다. ROOM1 돋보기는 유지하고 ROOM2에서는 사용하지 않는다.

## 1. 입력과 범위

이 플랜은 다음 대화에서 확정된 요구를 구현 단위로 정리한다.

- 획득 가능한 아이템은 고정 배경에 포함된 상태로 취급하지 않고 별도 표시 레이어를 사용한다.
- 필드 아이템 클릭은 즉시 획득하지 않고 `확인한다 / 획득한다` 선택을 연다.
- 확인 화면에서도 획득할 수 있다.
- 획득 성공 후 아이템 표시와 핫스팟을 함께 비활성화한다.
- 인벤토리는 화면 하단의 작은 패널로 바꾼다.
- 인벤토리 아이템 호버 시 이름과 한 줄 설명을 보여준다.
- 아이템 클릭 시 상세 확인과 취소를 제공하고, 휴대폰에는 명시적인 `사용`을 추가한다.
- 가방 버튼의 기존 열기/닫기를 유지한다.
- 인벤토리 영역 밖 클릭은 인벤토리만 닫고 같은 클릭으로 뒤의 방 핫스팟을 실행하지 않는다.
- ROOM1 돋보기는 유지한다. ROOM2 View/Controller에는 ROOM1 돋보기를 연결하지 않는다.

이 작업은 ROOM2 퍼즐 규칙, ROOM2 드래그 앤 드롭, 타이머, 저장/로드, 광고, 씬 전환, 최종 에셋 제작을 포함하지 않는다.

## 2. 성공 조건

ROOM1 이미지 기반 화면에서 다음이 플레이어에게 관찰되어야 한다.

1. 아직 소유하지 않은 획득 가능 아이템만 별도 오브젝트 레이어와 핫스팟으로 표시된다. 깨끗한 배경이 없는 동안 합성 배경 속 기존 그림이 남는 것은 허용된 임시 에셋 상태다.
2. 필드 아이템을 누르면 즉시 소유하지 않고 `확인한다 / 획득한다` 선택이 나타난다.
3. `확인한다`는 소유 상태를 바꾸지 않고 상세 표시를 연다. 상세 표시에서도 획득할 수 있다.
4. 획득에 성공하면 인벤토리에 정확히 한 번 추가되고, 필드 표시와 해당 핫스팟이 사라진다.
5. 획득에 실패하면 필드 표시, 핫스팟, 소유 상태가 그대로 유지된다.
6. 이미 소유한 아이템은 화면 재구성이나 재진입 시 다시 나타나지 않는다.
7. 하단 인벤토리는 방 화면 대부분을 가리지 않고, 아이템의 이름·설명·허용 행동을 분명하게 보여준다.
8. 휴대폰은 인벤토리 상세에서 `사용`할 수 있고 기존 휴대폰 화면을 연다.
9. 인벤토리 밖 클릭은 인벤토리만 닫으며 그 아래 ROOM1 상호작용을 같은 프레임에 실행하지 않는다.
10. 상태나 상호작용을 가진 방 요소는 화면 이미지가 아니라 독립된 방 오브젝트로 동작한다. 현재 화면은 오브젝트 상태를 보여주는 시점일 뿐 상태의 원천이 아니다.
11. 왼쪽·오른쪽 서랍은 독립된 상태 오브젝트이며, 각 서랍은 다시 클릭해 열고 닫을 수 있고 한쪽 상태가 다른 쪽을 바꾸지 않는다.
12. 기존 ROOM1 퍼즐과 돋보기 동작은 회귀하지 않는다.

## 3. 확정된 상호작용 계약

### 3.1 필드 아이템

필드 아이템의 기본 상태는 다음과 같다.

```text
미소유 → 아이템 레이어 표시 + 핫스팟 활성
소유   → 아이템 레이어 숨김 + 핫스팟 비활성
```

필드 아이템 클릭 시 선택창을 연다.

```text
[확인한다] [획득한다] [취소]
```

- `확인한다`: 확대 이미지와 설명을 표시한다. 소유·인벤토리·퍼즐 상태를 바꾸지 않는다.
- 상세 확인 화면: `[획득한다] [닫기]`를 제공한다.
- `획득한다`: 기존 인벤토리 추가 경로로 획득을 요청한다.
- `취소/닫기`: 어떤 게임 상태도 바꾸지 않고 현재 오버레이만 닫는다.
- 획득 성공: 인벤토리에 한 번 추가한 다음 표시와 핫스팟을 비활성화한다.
- 획득 실패: 표시와 핫스팟을 유지하고 실패 안내를 표시한다.
- 반복 클릭이나 화면 재구성은 중복 아이템을 만들지 않는다.

획득 결과는 Step 1에서 다음 세 값으로 고정한다.

| 결과 | 인벤토리 | 필드 레이어·핫스팟 | 안내 |
|---|---|---|---|
| `Acquired` | 정확히 한 번 추가 | 숨김·비활성 | 획득 성공 |
| `AlreadyOwned` | 변경 없음 | 실제 소유 상태에 맞춰 숨김·비활성 | 이미 소유 |
| `Rejected` | 변경 없음 | 표시·활성 유지 | 실패 이유 |

인벤토리가 소유 여부의 단일 진실 원천이다. 한 획득 요청은 동기적으로 한 결과만 반환하며, 같은 입력 시퀀스의 반복 요청은 추가 이벤트나 중복 아이템을 만들지 않는다.

첫 적용 대상은 현재 ROOM1 진행에 사용되는 `Phone`, `USB`, `Newspaper`, `PhotoFragment`다. 기존 도형 PrototypeUI의 찢어진 신문 조합 경로는 회귀 검증하되 이번 이미지 UX 개편의 주대상으로 확장하지 않는다.

### 3.2 공통 방 오브젝트 모델

ROOM1에서 상태 또는 플레이어 상호작용을 가진 요소는 독립된 **방 오브젝트**로 다룬다. 장식만 하는 배경 요소까지 전부 객체화할 필요는 없다.

각 방 오브젝트는 필요한 범위에서 다음 사실을 가진다.

```text
Identity          무엇인가
State             현재 상태가 무엇인가
Presentation      현재 상태를 어떤 레이어로 보이는가
Interaction       지금 어떤 입력을 받을 수 있는가
ContainedObjects  내부/위에 어떤 아이템이 있는가
```

적용 원칙:

- `RoomView`와 배경 이미지는 카메라/시점과 표현이다. 게임 상태의 단일 진실 원천이 아니다.
- 화면에 들어갔다는 이유로 오브젝트가 열리거나, 화면을 나갔다는 이유로 닫히지 않는다.
- 오브젝트 상태는 Controller의 명시적 전이로만 바뀐다.
- View는 Controller와 인벤토리의 실제 상태를 읽어 레이어와 핫스팟을 재구성한다.
- 오브젝트의 시각 레이어와 핫스팟 활성 조건은 같은 상태식에서 나온다.
- 한 오브젝트의 상태는 규칙이 명시적으로 연결하지 않는 한 다른 오브젝트 상태를 바꾸지 않는다.
- 획득 아이템은 소속 방 오브젝트의 자식/내용물로 취급한다. 컨테이너가 열려 있고 아이템이 미소유일 때만 표시·상호작용한다.
- 아이템 획득은 아이템 소유 상태만 바꾸며 컨테이너 상태를 암묵적으로 변경하지 않는다.
- 전체 화면 상세 이미지는 오브젝트를 자세히 보는 보조 시점으로 사용할 수 있지만, 오브젝트 상태 자체를 대신하지 않는다.
- 플레이 중 UI가 재생성되거나 시점을 왕복해도 Controller/인벤토리 상태에서 동일한 표현을 복원해야 한다.

ROOM1 적용 분류:

| 방 요소 | 종류 | 상태 원천 |
|---|---|---|
| 왼쪽·오른쪽 서랍 | 상태형 컨테이너 오브젝트 | Controller의 독립 Open/Closed 상태 |
| Phone·USB·Newspaper·PhotoFragment | 획득 아이템 오브젝트 | 인벤토리 소유 여부 |
| 출입문/전자 잠금장치 | 상태형 퍼즐 오브젝트 | `DoorUnlocked`, `RoomCleared` |
| 휴대폰 화면 | 소유 아이템의 단독 사용 UI | `PhoneUnlocked`와 현재 휴대폰 시점 |
| 시체·도구·고정 단서 | 비상태 또는 확인형 오브젝트 | 별도 진행 상태가 필요할 때만 추가 |
| 벽·바닥·장식 | 배경 | 객체화하지 않음 |

### 3.3 독립 서랍 오브젝트

서랍은 별도 전체 화면이 아니라 책상 화면 위의 상태 오브젝트다.

```text
Desk
├─ LeftDrawer: Closed / Open
│  └─ PhotoFragment
└─ RightDrawer: Closed / Open
   └─ USB
```

- 왼쪽 서랍 클릭은 왼쪽 상태만 토글한다.
- 오른쪽 서랍 클릭은 오른쪽 상태만 토글한다.
- 두 서랍은 동시에 열릴 수 있다.
- 열린 서랍을 다시 클릭하면 해당 서랍만 닫힌다.
- 서랍을 닫지 않아도 진행에 불이익이나 차단이 없다.
- 다른 화면을 확인하거나 책상으로 돌아와도 각 서랍 상태는 유지된다.
- `뒤로` 같은 시점 이동은 서랍 상태를 변경하지 않는다.
- 사진 조각은 `왼쪽 서랍 열림 && 미소유`일 때만 표시·클릭 가능하다.
- USB는 `오른쪽 서랍 열림 && 미소유`일 때만 표시·클릭 가능하다.
- 아이템 획득은 서랍 개폐 상태를 바꾸지 않는다.
- 기존 `PhotoDrawer`/`UsbDrawer` 전체 화면 교체는 일반 서랍 상호작용의 상태 원천으로 사용하지 않는다.
- 열린 서랍 누끼가 없으면 명확한 placeholder 레이어로 상태를 검증하고 이후 Sprite만 교체한다.

### 3.4 하단 인벤토리

- 인벤토리 창은 화면 하단에 고정된 소형 패널이다.
- 정확한 픽셀 크기와 열 수는 구현 단계에서 현재 3:2 ROOM1 화면으로 시각 검증하되, 기존 `7×9` 전체 화면형 패널은 유지하지 않는다.
- 가방 버튼은 항상 식별 가능하고 기존처럼 열기/닫기를 토글한다.
- 빈 슬롯은 필요한 수량 이상으로 화면을 크게 차지하지 않는다.
- 아이템 아이콘이 없더라도 이름으로 식별할 수 있어야 한다.

호버 표시는 다음 정보만 제공한다.

```text
아이템 이름
한 줄 설명
```

아이템 클릭은 즉시 사용하거나 소비하지 않고 상세 카드를 연다.

- 일반 아이템: `[확인] [취소]`
- 휴대폰: `[확인] [사용] [취소]`
- `확인`: 확대 이미지와 상세 설명을 표시한다.
- `사용`: 기존 `ItemUsed(Phone)` 경로를 통해 ROOM1 휴대폰 UI를 연다.
- `취소`: 상세 카드만 닫는다.
- USB 등 대상이 필요한 아이템은 인벤토리 안에서 임의로 퍼즐 성공을 만들지 않는다.
- 호버 입력이 없는 환경에서는 아이템 클릭으로 열리는 상세 카드가 이름과 한 줄 설명을 동일하게 제공한다.

### 3.5 UI 상태와 우선순위

한 번에 하나의 전면 상호작용만 활성화한다.

```text
Room
├─ FieldChoice
├─ FieldInspect
├─ InventoryOpen
│  ├─ ItemCard
│  └─ ItemInspect
└─ PhoneUI
```

- `FieldChoice`에서 확인하면 `FieldInspect`로 교체되고, 닫으면 방 화면으로 돌아간다.
- `InventoryOpen`에서 아이템을 클릭하면 패널 안의 `ItemCard`가 열리고, 확인하면 같은 영역이 `ItemInspect`로 전환된다. 별도 모달을 중첩하지 않는다.
- `ItemInspect`의 뒤로는 `ItemCard`, 취소는 인벤토리 기본 상태로 돌아간다.
- 가방 버튼으로 인벤토리를 열면 필드 선택/확인 오버레이를 닫는다.
- 필드 선택/확인 오버레이가 열린 동안 방 핫스팟과 돋보기 입력을 막는다.
- 인벤토리가 열린 동안 돋보기 렌즈는 숨기되 ROOM1 돋보기 기능 자체를 제거하지 않는다.
- 휴대폰 `사용` 성공 시 인벤토리를 닫고 기존 휴대폰 UI로 전환한다. 실패하면 인벤토리와 보유 상태를 유지하고 이유를 표시한다.

### 3.6 인벤토리 닫기와 입력 차단

- 가방 버튼 재클릭은 인벤토리를 닫는다.
- 인벤토리 패널·상세 카드·가방 버튼 바깥의 `pointer-down`으로 인벤토리를 닫는다.
- 해당 pointer-down부터 pointer-up까지의 입력 시퀀스 전체를 닫기 동작으로 소비한다. 같은 입력이 뒤의 ROOM1 핫스팟, 문, 서랍, 전화 입력 등을 실행해서는 안 된다.
- 인벤토리 닫기는 보유 아이템, 퍼즐 진행, `ItemAdded`, `ItemCombined`, `ItemUsed`를 변경하거나 발생시키지 않는다.
- 닫기는 상세 카드와 호버 같은 일시적 표시만 정리한다.
- 기존 `IInventoryAccess` 보유·추가·선택·조회 계약을 깨뜨리지 않는다. 향후 ROOM2 대상 사용을 위해 선택 상태를 닫기 부작용으로 임의 삭제하지 않는다.

### 3.7 돋보기 경계

- `Room1ImageNavigationUI`의 기존 돋보기는 이번 작업에서 제거하거나 재설계하지 않는다.
- 돋보기는 ROOM1 View 내부 기능으로만 남긴다.
- ROOM2는 별도의 `Room2PrototypeUI`/향후 ROOM2 View를 사용하며 `Room1ImageNavigationUI`나 돋보기 생성 코드를 부착·호출하지 않는다.
- ROOM2 암실 확대기는 방 오브젝트이며 ROOM1 돋보기와 공유하지 않는다.

## 4. 에셋 선행 점검

별도 아이템 Sprite가 존재한다는 사실만으로 합성 배경 속 기존 아이템이 사라지지는 않는다. 구현 전 화면별 에셋을 다음 표로 점검한다.

| 아이템 | 미획득 배경 | 획득 후 깨끗한 배경 | 별도 아이템 Sprite | 처리 |
|---|---|---|---|---|
| Phone | 점검 | 점검 | `phoneItem` 존재 | 가용 조합 확정 |
| USB | `usbDrawer` 점검 | 점검 필요 | `usbItem` 존재 | 깨끗한 배경 확인 전 임의 패치 금지 |
| Newspaper | 책상/신문 화면 점검 | 점검 필요 | `newspaperItem` 존재 | 단서 화면과 필드 표시 분리 |
| PhotoFragment | `photoDrawer` 존재 | `emptyPhotoDrawer` 존재 | `photoFragmentItem` 현재 미연결 | 실제 별도 Sprite 연결 여부 확인 |

Step 0의 아이템별 감사표에는 아이템 ID, 표시 이름, 한 줄 설명, 상세 설명, 미획득/획득 후 배경, 필드 Sprite, 상세 Sprite, 인벤토리 Sprite, 핫스팟 화면·좌표를 함께 기록한다. 누락된 표시 문자열은 enum 이름을 임시 표시하되 완료 조건으로 삼지 않고, 누락된 Sprite는 이름 표시로 식별 가능하게 하면서 에셋 부족으로 보고한다.

원칙:

- 아이템 없는 배경이 있으면 그 배경과 별도 아이템 레이어를 조합한다.
- 깨끗한 배경이 없으면 현재 합성 배경을 임시로 유지하고, 그 위에 별도 획득 오브젝트와 핫스팟을 올려 로직부터 완성한다.
- 획득 후에는 별도 오브젝트와 핫스팟만 사라진다. 배경에 구워진 기존 그림이 남는 것은 알려진 임시 시각 한계이며, 이후 깨끗한 배경 교체로 해결한다.
- 검은 사각형 등으로 배경을 가리거나 원본 PNG를 임의 보정하지 않는다.
- 별도 Sprite가 없는 아이템은 이름이 명확한 placeholder 오브젝트로 계약을 검증하고 `에셋 필요`로 기록한다.
- 원본 PNG를 수정하거나 새 최종 에셋을 생성하는 작업은 별도 승인 없이는 하지 않는다.

## 5. 책임 경계

### `Room1GameController`

- ROOM1 상태형 방 오브젝트의 상태와 명시적 전이를 소유한다.
- 현재 `RoomView`나 활성 Sprite를 게임 상태로 사용하지 않는다.
- `LeftDrawerOpen`과 `RightDrawerOpen`을 서로 독립된 상태로 유지한다.
- 서랍 토글과 아이템 획득을 서로 다른 전이로 제공한다.
- 획득 가능 여부와 실제 인벤토리 추가를 조정한다.
- 성공/이미 소유/인벤토리 실패 결과를 View에 전달한다.
- ROOM1 퍼즐 상태를 유지한다.
- 시각 레이아웃과 모달 구성을 결정하지 않는다.

### `Room1ImageNavigationUI`

- Controller/인벤토리 상태를 방 오브젝트 레이어와 핫스팟으로 투영한다.
- 시점 변경이나 UI 재생성이 오브젝트 상태를 암묵적으로 바꾸지 않게 한다.
- 필드 아이템 레이어, 핫스팟, 선택창, 상세 확인을 표시한다.
- Controller에 확인/획득 의도를 전달한다.
- 인벤토리에 직접 아이템을 추가하거나 퍼즐 성공을 결정하지 않는다.

### `InventoryManager`

- 하단 인벤토리, 호버 정보, 상세 카드와 허용된 단독 사용을 제공한다.
- ROOM1/ROOM2 퍼즐 규칙을 알지 않는다.
- 인벤토리 바깥 클릭을 닫기 동작으로 소비하고 방 입력 차단 여부를 노출한다.

### `Room1ImageLibrary`

- 배경, 필드 아이템, 인벤토리/상세 이미지의 교체 가능한 참조를 제공한다.
- 룰이나 소유 상태를 저장하지 않는다.

## 6. 순차 구현 단위

각 단계는 `구현 → 전체 diff 검토 → 정적/가능한 런타임 검증 → 로컬 커밋` 후 다음 단계로 넘어간다.

### Step 0 — 에셋·현재 동작 감사

수정 없이 다음을 기록한다.

- 네 아이템별 합성 배경/깨끗한 배경/별도 Sprite 대응표
- 현재 클릭 후 획득 및 재클릭 동작
- 인벤토리 열기/닫기, 슬롯 사용, 휴대폰 사용 동작
- 현재 ROOM1 돋보기 정상 동작

**완료 기준:** 각 아이템에 대해 레이어 분리가 가능한지 또는 어떤 에셋이 부족한지 명시되어 있다.

### Step 1 — 필드 아이템 상태 계약

- 테스트에서 미소유/확인/획득 성공/중복 방지/획득 실패 상태를 먼저 표현한다.
- Controller의 획득 결과를 View가 구분할 수 있게 최소 계약을 추가한다.
- UI와 에셋 배치는 아직 바꾸지 않는다.

**커밋 후보:** `feat: define room 1 field item interaction contract`

### Step 2 — 한 아이템 레이어 수직 슬라이스

상태 전환을 가장 명확히 확인할 수 있는 `PhotoFragment`를 우선 적용한다.

- 현재 빈 서랍 배경을 사용할 수 있으면 연결하고, 별도 조각 Sprite가 없으면 명확한 placeholder 조각 레이어 사용
- `확인한다 / 획득한다 / 취소` 선택창
- 상세 확인 화면에서 획득
- 획득 성공 후 레이어·핫스팟 비활성
- 재진입/재표시 시 소유 상태 반영

`photoFragmentItem`이 실제 Sprite에 연결되지 않았다면 최종 에셋을 임의 생성하지 않고 placeholder 오브젝트로 수직 슬라이스를 완성한다. 이후 Sprite 참조만 교체할 수 있어야 한다.

**커밋 후보:** `feat: add layered room 1 item interaction`

### Step 2.1 — 화면 중심 구현을 방 오브젝트 상태로 교정

공통 방 오브젝트 모델의 첫 적용으로 서랍과 그 내용물을 교정한다. Step 2에서 만든 사진 조각의 획득 결과와 선택/확인 UI는 유지하되, 전체 `PhotoDrawer` 화면에 붙인 배치를 책상 위 왼쪽 서랍 오브젝트로 옮긴다.

- Controller에 독립적인 `LeftDrawerOpen`, `RightDrawerOpen` 상태와 각 토글 추가
- 책상 화면을 유지한 채 왼쪽/오른쪽 서랍 레이어를 각각 표시
- 두 서랍 동시 열림과 개별 닫힘 허용
- 화면 이동과 `뒤로`는 서랍 상태를 바꾸지 않음
- 사진 조각 레이어·핫스팟을 열린 왼쪽 서랍의 자식 상태로 이동
- 오른쪽 서랍에는 기존 USB 획득 경로를 잃지 않도록 별도 USB 오브젝트를 표시하되, 확인/획득 선택 UI 전환은 Step 3에서 수행
- 획득 후 아이템만 사라지고 서랍 열림 상태는 유지
- 열린 서랍 최종 누끼가 없으면 placeholder 사용

**커밋 후보:** `refactor: model room 1 drawers as independent objects`

### Step 3 — 나머지 ROOM1 아이템 적용

Phone, USB, Newspaper에 동일 계약과 공통 방 오브젝트 모델을 적용한다.

- 각 아이템의 표시·핫스팟은 현재 시점 이름이 아니라 소속 오브젝트 상태와 인벤토리 소유 여부에서 계산한다.
- USB는 Step 2.1의 오른쪽 서랍 오브젝트 안에서 확인/획득 흐름을 제공하며 전체 `UsbDrawer` 화면으로 이동하지 않는다.
- 각 아이템은 확인만으로 획득되지 않는다.
- 획득 후 재클릭 불가
- 휴대폰은 획득 이후 인벤토리에서 사용 가능
- 깨끗한 배경이 없는 항목도 현재 합성 배경 위의 별도 오브젝트로 상태 전환을 구현하고, 임시 시각 한계를 명시한다.

**커밋 후보:** `feat: apply room 1 collectible choice flow`

### Step 4 — 하단 소형 인벤토리

- 기존 `7×9` 전체 화면형 UI를 하단 소형 패널로 교체
- 아이콘·이름 식별 보장
- 호버 이름/한 줄 설명
- 클릭 상세 카드
- 휴대폰의 명시적 `사용`
- 기존 신문 조합과 이벤트 동작 유지

**커밋 후보:** `feat: compact room inventory interactions`

### Step 5 — 바깥 클릭 닫기와 입력 소비

- 패널/카드/버튼 바깥 클릭으로 닫기
- 같은 클릭의 ROOM1 핫스팟 전파 차단
- 닫기 시 보유/진행/이벤트 무변경
- ROOM1 돋보기와 인벤토리 입력 충돌 회귀 검증

**커밋 후보:** `fix: close inventory without leaking room input`

### Step 6 — ROOM1 통합 검증

플레이 흐름으로 다음을 확인한다.

1. 각 필드 아이템 확인 후 취소 → 미획득 유지
2. 왼쪽·오른쪽 서랍을 각각 열고 닫기 → 반대쪽 상태 불변, 동시 열림 가능
3. 서랍을 열어둔 채 다른 화면 왕복 → 각 열림 상태 유지
4. 상세 화면에서 획득 → 인벤토리에 한 번 추가, 해당 서랍 상태 유지
5. 획득 후 필드 표시·핫스팟 비활성
6. 하단 인벤토리에서 이름·설명 확인
7. 휴대폰 `사용` → 기존 휴대폰 화면
8. 인벤토리 바깥 클릭 → 닫힘, 아래 핫스팟 미실행
9. 신문·USB·사진 조각과 ROOM1 탈출 조건 유지
10. 돋보기 기존 동작 유지
11. `IInventoryAccess` 기존 테스트 유지

**커밋 후보:** `test: verify room 1 item and inventory UX`

### Step 6.1 — ROOM2 전 공통 상호작용 추출 체크포인트

ROOM1 통합 검증을 통과한 실제 동작과 ROOM2의 첫 소비자를 함께 놓고 공통 메커니즘만 추출한다. ROOM1 구현을 이름만 바꿔 범용 프레임워크로 선언하거나, 아직 소비자가 없는 추상화를 미리 만들지 않는다.

반복이 확인된 후보:

```text
FieldItemInteraction             확인 / 획득 / 취소와 결과 처리
InventoryItemPresentationCatalog 이름 / 짧은 설명 / 상세 설명 / 허용 행동
CollectibleObjectPresentation    소유·컨테이너 상태에 따른 레이어·핫스팟
IItemUseTarget                   드래그 아이템 수용과 대상 사용 요청
ItemUseResult                    성공 / 잘못된 아이템 / 선행조건 부족 / 이미 완료
```

추출 기준:

- ROOM1에서 플레이 검증된 동작이고 ROOM2에 실제 동일 소비자가 있어야 한다.
- 공통 모듈은 아이템 ID, 표시 데이터, 획득 요청, 대상 사용 결과만 다룬다.
- ROOM1 휴대폰·신문·문 규칙과 ROOM2 USB·싱크대·확대기·키패드 규칙은 각 방 Controller/Rules에 남긴다.
- 모든 방 오브젝트를 하나의 거대 기반 클래스나 상태 enum으로 합치지 않는다.
- 기존 `Room1FieldItemAcquisition`처럼 메커니즘은 범용인데 이름만 방에 묶인 코드는 실제 ROOM2 사용 시점에 일반화한다.
- ROOM2 View는 확인된 공통 UI를 재사용하며 ROOM1 모달 코드를 복사하지 않는다.
- 추출 전후 ROOM1 통합 테스트가 동일하게 통과해야 한다.

**완료 기준:** ROOM2 Controller/View가 복사 없이 소비할 최소 공통 API와 ROOM1 회귀 증거가 준비되어 있다.

**커밋 후보:** `refactor: extract shared room interaction primitives`

## 7. 검증 전략

### 자동 검증

- 기존 `Room1BatchSmokeTest`의 휴대폰·USB·신문·사진 조각·출구 계약 유지
- `Acquired / AlreadyOwned / Rejected` 각각의 인벤토리·레이어·핫스팟 결과 검증
- 왼쪽/오른쪽 서랍의 독립 토글, 동시 열림, 시점 왕복 후 상태 유지 테스트
- 아이템 획득이 서랍 상태를 변경하지 않는 테스트
- 필드 아이템 확인이 소유 상태를 바꾸지 않는 테스트
- 획득 성공 시 한 번만 추가되는 테스트
- 실패/중복 시 필드 상태가 사라지지 않는 테스트
- 인벤토리 닫기가 아이템 수·선택·이벤트를 변경하지 않는 테스트
- 바깥 클릭이 방 입력으로 전파되지 않는 입력 경계 테스트
- `git diff --check`

자동 검증 실패나 `git diff --check` 실패 상태에서는 해당 단계의 커밋을 만들지 않는다. Unity 실행이 환경상 막힌 경우 정적/외부 하네스 결과와 미실행 사유를 커밋 보고에 분리해 기록하고 런타임 통과로 간주하지 않는다.

### 실제 Unity 확인

현재 프로젝트와 같은 `6000.3.22f1` Editor에서 다음을 확인한다.

- 3:2 Game View에서 하단 인벤토리 크기와 가독성
- 마우스 호버·클릭·바깥 클릭
- 선택창/상세 카드의 겹침과 입력 차단
- 필드 아이템 레이어 정렬과 획득 후 제거
- 휴대폰 사용과 돋보기 회귀

Unity가 이미 프로젝트를 열고 있을 때 별도 batch instance를 동시에 실행하지 않는다. 현재 Editor의 메뉴 테스트나 직접 Play 검증을 우선한다.

## 8. 중단 조건

다음 상황에서는 임의 구현하지 않고 해당 단계에서 멈춰 보고한다.

- 별도 Sprite 또는 placeholder를 현재 화면 좌표에 놓아도 플레이어가 획득 대상을 식별할 수 없음
- 합성 배경과 아이템 Sprite의 구도/크기가 달라 클릭 대상 자체를 오인하게 만듦
- 하단 인벤토리가 ROOM1 필수 핫스팟을 가려 정확한 배치 판단이 필요함
- 바깥 클릭 소비를 위해 ROOM1 외 다른 방 입력 구조까지 대규모로 바꿔야 함
- 기존 신문 조합이나 다른 담당자의 ROOM1 동작을 깨지 않고 변경할 수 없음

## 9. ROOM2와의 경계

이번 플랜은 ROOM2 퍼즐을 구현하지 않는다. Step 6.1에서 실제 ROOM2 소비자와 함께 공통 상호작용을 추출한 뒤 ROOM2 View/Controller를 구현한다. ROOM2도 같은 오브젝트 원칙을 따른다. 예를 들어 싱크대의 물/마개/사진, 컴퓨터의 메모 접근 상태, 확대기, 오른쪽 사진 조각 서랍은 화면 이름이 아니라 각각의 오브젝트 상태로 모델링해야 한다. 이후 ROOM2가 공유하는 것은 다음뿐이다.

- 지속되는 보유 아이템
- `IInventoryAccess`의 보유·추가·선택·조회 계약
- 축소된 공통 인벤토리 표현
- 향후 드래그 payload를 붙일 수 있는 아이템 UI

ROOM2는 `Room2Rules`, `Room2GameController`, `Room2PrototypeUI`와 ROOM2 전용 드롭 대상을 별도로 가진다. ROOM1 돋보기·필드 모달·배경 레이어 로직을 ROOM2에 복사하거나 import하지 않는다.
